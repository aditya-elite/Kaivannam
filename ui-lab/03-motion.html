Study 03

Motion, past the spec

The shipped spec covers reveals, the seal, the weave and page transitions. What is missing is mostly at the seams — the moment between two states. Below: four additions worth having, and three refusals with reasons, because the refusals are the more useful half.

1 · Thread-snap on form submit

Sealing a product is the emotional counterpart to verifying one, and right now it just disables a button. A thread drawing taut and knotting is the same vocabulary as the seal, used at the other end of the journey.

Submit confirmation

~30 lines
Runs once, ~940ms total, then stops — same discipline as the seal. Under reduced motion the thread renders drawn and the beads are simply present.

The registration flow's missing payoff moment.

2 · Scroll-linked kolam

The kolam divider currently draws on a 700ms timer once it enters view. Tying it to scroll position instead means the reader draws it at their own pace — and it costs no JS at all.

Divider driven by view()

progressive
↓ scroll this panel ↓
keep going

Your browser has no animation-timeline — the fallback (path fully drawn) is what you're seeing. 

/* motion.css — layered on top of the existing IO version */
@supports (animation-timeline: view()) {
  .kolam path {
    animation: draw-thread linear both;
    animation-timeline: view();
    animation-range: entry 10% cover 55%;
  }
}
Zero JS, zero scroll listeners, and where unsupported the existing IntersectionObserver version keeps working untouched.

Strictly better than what is there now.

3 · Stagger by position, not DOM index

Diagonal reveal order

index maths
By DOM index — reads as a queue
123456789
By row+col — reads as a wave
123456789
// delay = (row + col) * 60ms — the wave runs along the same diagonal
// axis as the §2.2 spine, so the two devices agree with each other.
const delay = (Math.floor(i / cols) + (i % cols)) * 60;
Same cost as the current stagger, and it happens to match the diagonal already used by the spine. On the artisan grid this is a noticeable improvement.

Change one line in the Reveal observer callback.

4 · Photo "develops" instead of fading

Stage photo entrance

transform only

A veil retracting with scaleY — not a blur. Blur-to-sharp is the obvious "developing" effect and it is exactly the expensive filter the spec rules out. This reads the same and composites on the GPU.

Pairs with the existing photo-settle rather than replacing it: settle for uploads the artisan just took, develop for photos arriving from the server.

Pick one per context. Using both in one view is noise.

Three refusals

Pointer-tracking card tilt

rejected
Meenakshi R.
Kanchipuram weaving

Move your pointer over the card. Now consider that the target device is a touchscreen, where this does nothing at all — so it is an effect built exclusively for the reviewers and not for the users. It also needs a mousemove handler per card and permanent will-change.

Zero reach on the actual device. Costs the most of anything here.

Counting-up stat numbers

rejected

The landing stats are inside a <dd>. Animating the text content means a screen reader can begin announcing "four hundred and twelve" and be interrupted with a different number. Fixing that means aria-hidden on the visible number plus a parallel live value — a lot of machinery so that a digit can spin.

Accessibility cost is real, benefit is decorative.

Parallax on artisan photographs

rejected

Parallax is already permitted for the thin edge ornament, where it moves a few pixels of decoration. Applying it to portraits means continuously repainting a large image while scrolling — the single most reliable way to drop frames on a low-end Android. The ornament exists precisely so this temptation has a cheap outlet.

Large-area repaint on the slowest devices we support.

Test that actually decides these. Chrome DevTools → Performance → CPU 4× slowdown, Network Slow 3G, then run the verification flow end to end. Anything that drops below 50fps there does not ship, however good it looks on a laptop.
